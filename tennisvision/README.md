# 🎾 TennisVision

테니스 영상 하나로 **심판 · 코치 · 기자 · 대회 운영**을 대신하는 앱.

| 역할 | 기능 |
|---|---|
| 심판 | 실시간 인/아웃 판정 + 테니스 규칙에 따른 자동 점수 계산 (폴트·레트·듀스·타이브레이크·코트 체인지) |
| 코치 | 샷 단위 분석 → 강점/약점 자동 진단 + 추천 드릴 |
| 기자 | 포인트별 재미 점수로 하이라이트 자동 선정 및 클립 컷 |
| 대회 | Glicko-2 레이팅 기반 매칭, 랭킹, 풀리그/토너먼트/사다리 리그 |

핵심 설계는 **분석과 매칭이 한 덩어리**라는 것이다. 경기를 분석할 때마다
레이팅·플레이스타일 벡터·누적 통계가 갱신되고, 매칭과 리그 시딩은 그 값만 본다.
즉 많이 칠수록 매칭이 정확해지고, 매칭이 정확해질수록 분석할 경기가 늘어난다.

```
경기 영상/라이브 ──분석──▶ 포인트 · 샷 · 판정 · 하이라이트
                              │
                              ├──▶ 누적 통계 → 코칭 리포트
                              ├──▶ 플레이스타일 벡터(10축)
                              └──▶ Glicko-2 레이팅
                                       │
                     매칭 큐 ──────────┴──▶ 추천 상대 ──▶ 새 경기
                     리그/토너먼트 ─────────────────────▶ 새 경기
```

## 빠르게 돌려보기

```bash
cd tennisvision
pip install -r requirements.txt

# 1) 합성 테스트 경기 생성 (실제 영상이 없어도 전체 흐름을 볼 수 있다)
python tools/simulate.py --out data/sample_match.webm --points 10

# 2) 파이프라인 정확도 측정 (정답과 비교)
python tools/evaluate.py --video data/sample_match.webm

# 3) 데모 데이터 채우기
python -m server.seed

# 4) 앱 빌드 + 서버 실행
cd app && npm install && npm run build && cd ..
python -m uvicorn server.main:app --port 8000
```

`http://localhost:8000` 접속. API 문서는 `/docs`.

폰에서 라이브 심판을 쓰려면 카메라 권한 때문에 HTTPS 또는 `localhost` 가 필요하다.
같은 와이파이의 폰에서 접속하려면 `--host 0.0.0.0` 으로 띄우고 터널(ngrok 등)로 HTTPS 를 붙인다.

```bash
python -m pytest tests/ -q          # 규칙·기하·레이팅·리그 로직 테스트
```

## 어떻게 판정하는가

### 1. 코트 캘리브레이션
앱에서 복식 코트 4모서리를 탭하면 이미지↔코트 호모그래피가 만들어진다.
`detect_court()` 로 자동 인식도 시도하지만(라인 마스크 → 허프 → 모델 재투영 점수),
정확도가 판정 품질을 좌우하므로 **수동 4점이 기본 경로**다.

### 2. 왜 "바운스 순간"에만 판정하는가
공중의 공을 지면 호모그래피로 투영하면 실제보다 카메라에서 먼 쪽으로 밀린
"겉보기 지면 위치" G 가 나온다. 카메라 바로 아래 지점을 N 이라 하면

```
G = N + k·(P − N),   k = 카메라높이 / (카메라높이 − 공높이) ≥ 1
```

바운스에서는 공 높이가 0이라 **k = 1, 즉 G = P**. 그래서 판정은 오직 바운스
시점에서만 정확하고, 엔진도 거기서만 판정한다.

### 3. 이벤트 검출 (바운스 vs 라켓 타격)
같은 관계식에서 이벤트 구분도 따라 나온다.

- **바운스**: 수직 속도만 뒤집히므로 겉보기 속도의 불연속이 N 방향(반경)으로만 생기고, 크기는 대략 `2·|v_수직|`
- **라켓 타격**: 공이 통째로 되돌아오므로 크기가 대략 `2·|v|` 로 훨씬 크고 접선 성분이 함께 생긴다

그래서 `|Δv| / 공속도` 하나로 둘을 가른다. 픽셀이 아니라 지면 m/s 로 재기 때문에
코트 안쪽/바깥쪽, 해상도, fps 가 달라져도 같은 임계값이 통한다.

바운스 위치는 검출된 프레임을 그대로 쓰지 않는다(30fps 에서 공은 프레임당 1m 씩
움직인다). 앞뒤 궤적에 2차 곡선을 각각 맞추고 **두 곡선의 교점**으로 서브프레임
위치를 복원하므로, 바운스 순간에 공이 안 잡혀도 앞뒤만 있으면 복원된다.

### 4. 판정은 확률이다
호크아이도 공칭 오차를 공표한다. 여기서는 캘리브레이션 오차 + 프레임 샘플링
한계 + 검출 오차 + **이벤트 자체의 확신도**를 합쳐 1σ 오차 예산을 만들고

```
P(인) = Φ( (라인까지의 여유 + 공 반지름) / σ )
```

로 확률을 낸다. 여유가 오차 예산 안이면 `too_close = true` 로 "판독 불가"를
표시한다. 애매한 판정을 확신에 찬 콜처럼 내보내지 않는 것이 이 모듈의 원칙이고,
그래서 앱에는 **되돌리기·수동 득점·판정 뒤집기**가 항상 함께 있다.

## 정확도, 그리고 정직한 한계

`tools/evaluate.py` 는 합성 경기(정답 포함)로 다음을 측정한다.

| 항목 | 합성 영상 1280×720 / 30fps 기준 |
|---|---|
| 캘리브레이션 재투영 오차 | < 1mm (수동 4점) |
| 공 추적 정확도 | 검출된 프레임의 **오검출 0.5%**, 프레임 검출률 약 80% |
| 바운스 위치 오차 | 중앙값 **약 10cm**, p90 약 60cm |
| 바운스 검출 재현율 | 약 50–60% |

즉 **잡아낸 바운스의 위치는 꽤 정확하지만, 바운스를 다 잡지는 못한다.**
합성 영상의 공이 원거리에서 2px 밖에 안 되는 탓이 크고, 실제 영상에서는
다음으로 개선된다.

- **60fps 촬영** — 이벤트 시간 해상도가 2배가 된다(가장 효과가 크다)
- **딥러닝 검출기 연결** — 가중치를 준비하면 코드 수정 없이 교체된다

  ```python
  from engine.vision import detectors
  detectors.try_register_optional()                       # 설치된 것만 등록
  detectors.use("ball", "tracknet", weights="models/tracknet.pt")
  detectors.use("player", "yolo", weights="yolov8n.pt")
  ```
  추적·이벤트·판정 로직은 그대로 재사용된다.

측정값의 성격도 리포트에 그대로 적어 둔다.

- `speed_kmh` 는 타격 지점 → 바운스 지점의 **지면 투영 평균 속도**다. 3D 궤적
  길이와 공중 체류를 무시하므로 실제 라켓 스피드보다 낮게 나온다. 절대값보다
  같은 영상 안에서의 상대 비교에 쓰는 것이 맞다.
- `depth` / `lateral` 은 바운스 순간 값이라 신뢰도가 높다.
- 스핀은 단안 카메라로 직접 측정할 수 없다. 드롭샷·로브처럼 궤적으로 확실히
  구분되는 것만 라벨을 붙인다.
- `engine/umpire/trajectory.py` 의 3D 복원(물리 제약 최소자승)은 관측이 깨끗할
  때는 mm 수준으로 정확하지만 1px 노이즈에서 깊이 오차가 급격히 커진다.
  그래서 **기본 경로가 아니라 고품질 입력용 선택 모듈**로 둔다.

경기마다 `quality.overall` 을 계산해 앱 상단에 신뢰도로 표시하고, 낮으면
무엇을 고쳐야 하는지(캘리브레이션/조명/fps) 문구로 알려 준다.

## 코트에서 폰으로 쓰기

**앱 설치는 필요 없다.** PWA 라서 폰 브라우저로 열고 "홈 화면에 추가"만 하면
전체화면 앱처럼 뜬다. 다만 한 가지 제약이 있다.

> 브라우저는 `localhost` 가 아닌 주소에서는 **HTTPS 일 때만** 카메라를 허용한다.
> 같은 와이파이에서 `http://192.168.x.x:8000` 으로 들어가면 화면은 보이지만
> 카메라가 절대 열리지 않는다.

그래서 로컬 전용 인증서를 만들어 HTTPS 로 띄운다.

```bash
python tools/make_cert.py          # 랜 IP 가 들어간 자체 서명 인증서 생성 (certs/)
python -m uvicorn server.main:app --host 0.0.0.0 --port 8443 \
    --ssl-keyfile certs/key.pem --ssl-certfile certs/cert.pem
```

윈도우 방화벽에서 인바운드를 한 번 열어야 한다(**관리자 PowerShell**에서 실행,
같은 랜 안에서만 접근 가능하도록 범위를 제한한다).

```powershell
New-NetFirewallRule -DisplayName "TennisVision 8443" -Direction Inbound -Protocol TCP -LocalPort 8443 -Action Allow -RemoteAddress LocalSubnet
```

폰에서 `https://<PC의 랜 IP>:8443` 접속 → 첫 접속 때 "연결이 비공개로 설정되어
있지 않습니다" 경고가 뜨면 **고급 → 계속**. 그 뒤로는 보안 컨텍스트로 취급돼
카메라가 열린다. 인증서는 이 컴퓨터 밖으로 나가지 않고, 서버도 공인망에
노출되지 않는다.

체크리스트

1. PC 와 폰이 **같은 와이파이**. (코트에 공유기가 없으면 폰 핫스팟에 PC 를 붙이고
   `python tools/make_cert.py` 를 다시 실행해 핫스팟 IP 를 인증서에 넣는다)
2. 라이브 화면에서 전송 fps 를 **12~15** 로 둔다. 와이파이가 약하면 더 낮춘다.
3. 폰 화면이 꺼지면 프레임 전송이 멈춘다(브라우저가 렌더 루프를 정지시킨다).
   화면 자동 꺼짐을 꺼 두거나 최대로 늘려 둔다. 앱이 감지하면 경고를 띄운다.
4. 삼각대 고정. 캘리브레이션 후에는 카메라를 건드리지 않는다.

집에 PC 를 두고 코트에서 LTE 로 쓰려면 터널(cloudflared 등)로 공개 HTTPS 주소를
만들 수 있지만, 그건 로컬 서버를 인터넷에 노출하는 것이므로 별도로 판단해서
설정한다. 업로드 대역폭도 15fps 기준 10Mbps 이상 필요하다.

## 촬영 가이드

1. 삼각대에 폰을 고정한다. **손으로 들면 판정이 무너진다.**
2. 베이스라인 뒤, 지면에서 2m 이상 높은 곳. 코트 4모서리가 모두 화면에 들어와야 한다.
3. 가능하면 60fps, 1080p.
4. 경기 중 카메라를 옮기지 않는다. 세션이 코트 라인 일치도를 주기적으로 확인해
   흔들림을 감지하면 재캘리브레이션을 요청한다.

## 매칭은 무엇을 보는가

추천 점수는 다섯 축의 가중합이고, 앱은 각 축의 기여도를 그대로 보여 준다
(왜 이 사람을 추천했는지 설명할 수 없으면 쓰지 않는 기능이 된다).

| 축 | 가중치 | 내용 |
|---|---|---|
| 실력 균형 | 42% | Glicko-2 예측 승률이 50%에 가까울수록 높다 |
| 시간대 | 20% | 매칭 큐에 올린 가능 시간이 겹치는 시간 |
| 거리 | 15% | 좌표 거리 또는 같은 홈 코트 |
| 스타일 궁합 | 13% | 10축 스타일 벡터의 유사도(비슷/상반/적당히 다름 선택) |
| 새로움 | 10% | 최근 90일 대결 횟수가 많으면 감점 |

**Elo 가 아니라 Glicko-2 를 쓰는 이유**: 동호인 테니스는 경기 수가 적고 불규칙해서
"이 사람 실력을 얼마나 확신하는가"가 중요하다. 신규 유저는 편차(RD)가 커서 몇
경기 만에 제자리를 찾고, 오래 쉰 유저는 RD 가 다시 벌어져 과도한 점수 이동을
막는다. 테니스 특성상 6-0 과 7-6 을 구분해야 하므로 게임 득실을 섞은 결과값을
기본으로 쓴다(`ratings.score_outcome`).

리그는 풀리그(서클 방식, 홀수 인원 부전승 처리) · 단판 토너먼트(레이팅 시딩,
1번 시드와 2번 시드가 반대편) · 사다리(3계단 위까지 도전)를 지원하고, 결과는
전부 같은 레이팅으로 흘러 들어간다.

---

## 주요 API

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/api/matches/upload` | 영상 업로드 → 백그라운드 분석 |
| GET | `/api/matches/{id}` | 리포트 전체(포인트·판정·하이라이트·통계·코칭·스타일) |
| GET | `/api/matches/{id}/shots` | 샷 단위 데이터 |
| POST | `/api/matches/{id}/calls/{callId}/override` | 판정 뒤집기(챌린지) |
| WS | `/ws/live/{sessionId}` | 실시간 심판 — 프레임(binary JPEG) 업로드, 판정/점수 수신 |
| GET | `/api/matchmaking/suggestions` | 추천 상대 + 점수 분해 |
| POST | `/api/matchmaking/run` | 열린 요청들 자동 페어링 |
| GET | `/api/ladder` | 랭킹 보드 |
| POST | `/api/leagues/{id}/start` | 대진 생성 |
| POST | `/api/fixtures/{id}/result` | 결과 입력 → 순위표 + 레이팅 반영 |

### 실시간 세션 프로토콜

```jsonc
// 1) 클라이언트 → 서버
{"type":"init","calibration":{"imagePoints":[[x,y],[x,y],[x,y],[x,y]],"frameSize":[960,540]},
 "format":"one_set","names":{"near":"김민수","far":"이지현"},"firstServerSide":"near","fps":15}
// 이후 프레임은 binary JPEG 으로 전송

// 2) 서버 → 클라이언트
{"type":"ball","image":[x,y]}                       // 궤적 오버레이
{"type":"call","kind":"out","marginCm":-12.4,"errorBudgetCm":5.1,"tooClose":false,"announce":"아웃 — 12cm"}
{"type":"point","winnerSide":"near","reason":"winner","score":{...},"announce":"30 대 15"}
{"type":"warning","code":"camera_moved"}
{"type":"finished","matchId":42}

// 3) 수동 개입
{"type":"undo"} · {"type":"award","side":"near"} · {"type":"override","frame":123,"kind":"in"}
```

판정 지연은 `검출기 1프레임 + 이벤트 창 5프레임 + 비최대 억제 5프레임 ≈ 11프레임`.
30fps 에서 약 0.37초, 60fps 에서 약 0.18초다.

## 앞으로

- TrackNet/YOLO 가중치 번들 + 온디바이스(TFLite) 경량화
- 복식 지원(현재 데이터 모델은 준비돼 있고 추적이 2명 기준)
- 스윙 자세 분석(포즈 추정 기반 폼 피드백)
- 클럽 단위 다인 리그 스케줄러 · 코트 예약 연동
